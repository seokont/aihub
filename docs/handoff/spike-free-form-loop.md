## (2) Register `odoo_search` in BOTH modes

So that A and B differ **only** by the loop. Read `mcp/odoo/src/moni_mcp_odoo/server.py`'s registry:
`ToolSpec(name, action_class, description, handler, parameters, injected)` with
`DEFAULT_INJECTED = ("user_context", "context")` and the wrapper generated by `make_mcp_tool(spec)` from
`_signature_source`. `odoo_search` is `action_class="read"` and takes only declared parameters (no injected
beyond the defaults), so it appears in the advertised schema exactly like the other read tools.

**The I/O wrapper** (`search.py` stays pure; put the I/O beside it):

* `build_query(...)` is the **only** way to construct a request — no second path;
* two calls through the existing per-user client: `search_count` for the total, then `search_read` with
  `fields`, `limit`, `offset`, `order`;
* return `{records, count, limit, offset, model, fields}` so the loop (and the pipeline) can page;
* **the audit row** (who, model, fields, domain, record count) — the action name and the store call follow
  the existing `policy_client.py` / `audit_store.record(...)` pattern; a read is audited here because
  §3.8's "who read what" is otherwise unanswerable for an open-ended search;
* **`money_fields` seeding on the B path**: the request's `SearchQuery.money_fields` is what the anonymiser
  must be seeded from, so a level-B search result does not rely on a pattern that does not match amounts
  (the fallback pass did **not** match `amount_total: 152340.50` when unseeded). This is the same "router
  seeds the anonymiser on the external path" decision as 2b, applied to the search tool.

## (3) The loop behind `LLM_LOOP`

A **small function with an injectable model**, tested with the scripted-model harness, guards in code and
none in the prompt:

1. **Strict grounding as code.** Factual claims about company data require a successful tool result. Chat,
   clarifying questions and general explanations stay free — the distinction is a code check on what the
   loop produced, not an instruction.
2. **Post-loop classification into the existing typed reasons** (`no_answer_reason`): the audit keeps "why
   nothing was produced" — refusals, failures, caps and blank/control-token text each keep their own code and
   Ukrainian message, computed together as `_no_answer` already does.
3. **Deterministic check instead of a model verify:** numbers and ids asserted in the answer must appear in
   the tool results. A claim that cannot be traced is not grounded, and the check is testable without a model.
4. **Writes stop at the card:** a write tool call pauses for approval, with tests for
   **continue-after-Approve** and **continue-after-Deny** (the denial must leave no execution row — the
   `executed is True` filter landed in `3e5c8ee`).
5. **No local→cloud escalation.**
6. **Caps:** loop cap and token cap, named constants, and the loop's exit must produce one of the typed
   reasons — never a bare "the loop ended".

**Compose:** `LLM_LOOP: ${LLM_LOOP:-0}` on every service that runs the agent (see the "where the run
executes" row above), plus `.env.example` documenting it and the smoke delivery test that asserts it reaches
both services by name — the F12 class has bitten three times.

## (4) `scripts/benchmark_chat.py`

* **Targets nginx**, not the gateway: `http://127.0.0.1:${NGINX_HTTP_PORT:-80}` with the OpenAI-compatible
  chat route.
* **Two modes:** `--target main|spike` and `--loop 0|1`, plus a **baseline mode for the current main image**
  so the "before" numbers can be re-measured without rebuilding.
* **Five fixed questions:** my tasks · order S20013 · partner lookup · stock · create-task-with-approval.
  Plus the **"all my tasks" paging question, expecting 43 not 10** — the first cut of `odoo_search` must page
  (`limit` default 20 → 21+21+1 for 43 at 21 per page).
* **5 trials per question**, except the create-task row which is **n=1**: it writes to real Odoo. Task names
  are prefixed **`[bench]`**, the harness **prints the created task names at the end**, and there is **no
  automatic deletion** — the operator deletes them by hand.
* **Checkable completeness** per trial: the expected fact is present (task count, order state, partner id,
  stock quantity, created task id), **no `{PLACEHOLDER}`** survives in the reply, and **no control token**
  (`DONE`/`CONTINUE`) appears.
* Columns: seconds, model calls, completeness pass/fail, notes. Writes a markdown table to `--out`.
* **Token:** the password comes from **`$env:MONI_TEST_USER_PASSWORD`**, never typed and never printed; the
  client id to be read from the realm export or the existing token helper. Decoding a JWT for diagnostics
  must convert **base64url → base64** (`-`→`+`, `_`→`/`, pad) before `FromBase64String`.

after use, and keep `MONI_CRED_KEY` identical wherever it is restored, or the keys cannot be decrypted.
